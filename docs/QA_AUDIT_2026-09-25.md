## Actual Architecture

React 19/Vite/React Router, Node built-in HTTP, scrypt password hashes and persisted opaque bearer sessions. Tokens are kept in `sessionStorage`; permissions, status and assignments are checked by the server. This is not Express/JWT/Socket.IO. Browser storage does not approve students.

Production frontend configuration requires HTTPS backend access and fails closed when absent/invalid. Explicit development demonstration mode remains available. JSON storage serializes atomic writes in one process; MongoDB stores a revision-checked application-state document and retries conflicting updates. Empty production MongoDB and production JSON storage fail closed. Updates travel through authenticated HTTP polling (normally 15 seconds, student home 30 seconds) and refresh after writes, not sockets.

Approval and verified email are separate. Trips have distinct journey IDs, recorded start/end times, direction, accepted GPS, and conductor counts. Return journeys reverse the configured stop sequence; this does not establish independently surveyed return-road geometry. ETA is a qualified coordinate-distance approximation, not traffic-aware road routing.

## Unresolved Risks And Required Owner Actions

1. **Credential gate:** establish whether previously exposed demonstration accounts were rotated/disabled and revoke their sessions. Do not publish real credentials in docs or `VITE_*`. Existing public credentials remain for isolated fixtures only.
2. **Runtime gate:** approve a supported Node major (24.19.0 was tested), then align package engines, local pin and both hosting settings together. Runtime alignment was requested but not approved during this audit.
3. **Hosted configuration:** confirm `NODE_ENV`, `SMARTTRANSIT_STORAGE`, `SMARTTRANSIT_MONGODB_URI`, `SMARTTRANSIT_MONGODB_DB`, `SMARTTRANSIT_ALLOWED_ORIGIN`, `SMARTTRANSIT_OTP_SECRET`, `SMARTTRANSIT_EMAIL_PROVIDER`, `SMARTTRANSIT_BREVO_API_KEY`, `SMARTTRANSIT_MAIL_FROM`, `VITE_USE_BACKEND` and `VITE_API_BASE_URL`. Secret values were not read. The stricter startup validation can intentionally prevent a misconfigured deployment from starting.
4. **Real devices:** Android Chrome and iPhone Safari foreground GPS, permission recovery, weak accuracy, loss of data service, background/screen lock, reopening, battery behavior, keyboard/safe areas and text zoom remain untested. A website cannot promise uninterrupted locked-screen tracking from these desktop tests.
5. **Transport validation:** university staff must verify pickup-side stop pins, actual outbound/return roads, speeds/dwell times, contacts and support ownership. Historical IU-R9 duplicate-pin/data findings were not re-read from private production data. No fresh coordinate survey/geocoding was performed. Approximate ETA is not exact road distance or traffic prediction.
6. **External systems:** real Brevo delivery, social preview validation on intended platforms, Atlas backup/restore, hosted CORS/TLS/header behavior after release, alerts reaching humans and actual response coverage are not proven. In-app reports are not an emergency dispatch service.
7. **Scalability/security review:** per-process rate limiting and trust of forwarded IP headers need hosting/proxy review; no header-spoof attack was run on production. Synchronous scrypt, one-document Mongo state, document-size growth and high concurrency need realistic load measurements before university scale. Browser bearer storage remains XSS-sensitive; no auth redesign was made. Full Git history secret scanning, third-party penetration testing and log-redaction review were outside this bounded pass.
8. **Retry boundary:** write retries reuse IDs while the same form/provider remains mounted. There is no durable offline emergency queue. After closing/reloading during an uncertain submission, inspect authoritative history before re-entering it; cross-reload draft/idempotency persistence is an optional separately reviewed improvement.
9. **Product acceptance:** independent return-road definitions, richer background mobile tracking, map-provider traffic routing, server-side HTTP 404 hosting, telemetry/monitoring and broader browser support are proposals, not silently introduced requirements.
